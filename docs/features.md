## 实时资源指标

**解决的问题：** 判断 GPU 是否忙碌、显存是否充足，以及温度、功耗或频率是否异常。

NVML 提供 GPU 利用率、显存总量/已用/空闲、温度、功耗、风扇速度、图形/SM/显存时钟及编码器、解码器忙碌率。界面显示可用指标，对硬件不支持或读取失败的项目显示 `N/A` 并提供错误说明。

显存有两个不同维度：

- **容量占用**：`used / total`，用于判断可供任务分配的显存余量。
- **Memory I/O Busy**：NVML 的显存读写忙碌率，用于观察显存活动程度。

两者不能互相替代。比如任务可以分配大量显存但暂时不执行计算，此时容量占用较高，GPU 和显存忙碌率仍可能很低。各字段单位见[数据接口](data-model.md)。

## 多 GPU 总览与详情

**解决的问题：** 在多卡或混合型号机器上定位设备，比较资源余量，并查看某一张卡的完整信息。

桌面端多卡模式使用网格卡片，显示 GPU 编号、PCI 地址、负载、已用/总显存、占用比例和温度、功耗、风扇摘要。支持按设备名称、索引或 UUID 筛选。

`View Details` 打开所选 GPU 的完整详情，包括驱动、CUDA 驱动支持版本、UUID、功耗上限、时钟及更多利用率指标。单卡环境直接使用同一详情界面，避免单卡和多卡使用不同的数据来源。

UUID 用于保存设备状态，索引用于显示和导航。这使设备顺序变化时，历史仍属于原设备。

## 终端交互监控

**解决的问题：** 在 SSH 会话或有限终端空间中浏览所有 GPU 和进程。

运行 `gpu-monitor` 或 `gpu-monitor --watch` 进入 TUI。界面一次显示一张选中 GPU 的详情，每张 GPU 保存独立的进程滚动位置。表格按当前窗口实际高度计算可见行数，窗口缩小时先压缩曲线；低于 42 列 × 14 行时提示调整尺寸。

| 按键 | 操作 |
| --- | --- |
| `→`、Tab、`]` | 下一张 GPU |
| `←`、Shift+Tab、`[` | 上一张 GPU |
| `↑` / `↓`、`k` / `j` | 向上 / 向下滚动进程 |
| PageUp / PageDown | 按可见行数翻页 |
| Home / End | 到进程列表顶部 / 底部 |
| `r` | 请求重新初始化并立即采样 |
| `q`、Escape、Ctrl-C | 退出 |

首次采样立即执行。默认刷新间隔为 1000 毫秒，`--interval` 可调整，最小为 100 毫秒。采样在 TUI 事件循环中同步执行，驱动响应时间也会影响实际刷新和键盘响应。

终端会话负责进入和恢复 raw mode、备用屏幕；正常退出、返回错误及 panic 展开时执行恢复处理。

## 负载与显存历史

**解决的问题：** 区分持续负载、短时波动与采样中断，避免只凭当前数字判断任务状态。

| 行为 | GUI | TUI |
| --- | --- | --- |
| 保存范围 | 最近 60 秒内收到的样本 | 最近 60 个样本 |
| 横轴 | 按真实时间位置绘制 | 按样本顺序绘制 |
| 稳定读数 | 新时间戳仍追加；重复缓存快照不追加 | 同样记录新采样，重复时间戳不追加 |
| 缺测 | 空值或超过 2.5 秒的间隔打断连线 | 使用 `×` 表示缺失值 |
| 窄窗口 | 在固定时间窗口内缩放 | 显示能容纳的最新样本 |

因此，TUI 的 60 个样本不固定对应 60 秒，实际范围受刷新间隔和采样耗时影响。

GUI 的历史保存在卡片之外，筛选设备、切换详情或出现临时错误时仍然保留。全局错误或单卡错误会保留最后一次数据并标记为过期，恢复后按新的采样时间继续记录。历史不写入磁盘。

## GPU 进程查询

**解决的问题：** 找到占用显存的进程，并区分计算与图形任务。

采集器分别查询计算进程和图形进程，在同一 GPU 内按 PID 合并结果：同时出现在两类查询中的进程标为 `Mixed`。两次查询报告的是同一进程的显存分配，合并时采用可用值的较大者，避免重复相加。

进程按显存用量降序排列，相同时按 PID 排序；未知显存排在有数值的项目之后。进程名来自 `/proc/<pid>/comm`，文件不可读时显示 `unknown`，名称也可能受到系统长度限制。

桌面端详情页和 `View Processes` 弹窗复用进程展示组件，支持按名称或 PID 搜索。弹窗支持键盘操作，Escape 关闭后将焦点返回打开它的按钮。

CLI 的 `gpu-monitor processes` 提供单次进程列表；`gpu-monitor --json processes` 用于脚本读取。此子命令执行一次采样，即使同时指定 `--watch` 也不会持续输出。

若某一类进程查询失败，界面标记结果不完整并展示已取得的条目。空列表只有结合查询状态才有意义；未知进程显存显示为 `N/A`，不表示占用为零。此功能不提供进程终止或 GPU 参数修改。

## 异常提示与自动恢复

**解决的问题：** 在驱动暂时不可用、单卡失联或指标受限时，继续使用仍有效的数据，并判断数据是否新鲜。

采集结果区分全局错误、设备错误和指标错误。单张卡查询失败时继续采集其他卡；某项指标不可用时保留同一卡上的其他指标。持续监控时，初始化和枚举错误会自动退避重试，GUI 的 Retry 和 TUI 的 `r` 可请求提前重试。

GUI 显示以下状态：

| 状态 | 含义 |
| --- | --- |
| Connecting | 首次请求尚未返回快照或错误 |
| Live | 已收到快照，当前没有全局/设备故障或过期数据；具体指标仍可能为 `N/A` |
| Stale | 存在全局/设备故障，或快照、设备数据超过 3 秒未更新 |
| Offline | 尚无可展示的设备数据，且收到服务或设备错误 |

设备卡片同时显示采样时间。`Live` 表示数据的新鲜度，不代表 GPU 空闲，也不代表每项硬件能力都可用。TUI 直接显示设备失败数、局部错误以及保留数据的 `STALE` 标记。

重试通过采样服务执行，无法强制中断已经阻塞的驱动调用。并发和恢复边界见[系统架构](architecture.md)。

## 文本快照与脚本接入

**解决的问题：** 在不启动交互界面的情况下查询状态，或将监控数据交给其他程序处理。

| 命令 | 输出 |
| --- | --- |
| `gpu-monitor --once` | 单次可读文本 |
| `gpu-monitor --json` | 单次 JSON 对象 |
| `gpu-monitor --watch --json` | 每次采样一行 JSON 对象 |
| `gpu-monitor processes` | 单次可读进程列表 |
| `gpu-monitor --json processes` | 单次 JSON 进程快照 |

JSON 中保留设备归属、采样时间和各层错误。单次命令先输出快照，再以退出码表示全局失败或全部设备失败；部分失败仍允许返回可用结果。连续 JSON 模式在采集错误后继续输出错误快照和重试。

字段结构、空值含义与退出码见[数据接口](data-model.md)。
